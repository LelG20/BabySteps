## How the browser-to-database flow works

1. **The browser loads the page.** `lelg.html` provides the page structure, form and semantic controls. Its head links `styles.css`, and the deferred `script.js` runs after HTML parsing. The CSS controls appearance, including responsive layout; JavaScript behavior depends on matching IDs/classes in the HTML.
2. **The visitor may interact before submitting.** The menu button causes `script.js` to add/remove `is-open`, update `aria-expanded` and button labels, close on navigation click/Escape, and close after resizing above 680px. The learning-tip button displays a tip and cycles its array index. These are browser-side behaviors; CSS supplies the corresponding visual states.
3. **The visitor submits the contact form.** HTML names the submitted keys `name`, `email`, `subject`, and `message`; method is POST and action is `contact.php`. `novalidate` disables built-in form validation UI. The JS submit handler checks required fields and email validity, focuses errors and writes to the status region. When its checks pass, it does not cancel default submission, so the browser can POST normally. Client-side checks improve interaction but can be bypassed and are not a security boundary.
4. **PHP receives and validates the request.** `contact.php` rejects non-POST requests (405), reads and trims string values, requires name/email/message, validates email format, and enforces limits. Validation failures return 422. These server checks are authoritative for acceptance; they run even if browser code is bypassed.
5. **PHP obtains connection settings and writes data.** It loads the array from `config.php`, builds a MySQL DSN, connects using PDO, and prepares an INSERT into `contact_messages`. Named parameters keep submitted text separate from SQL syntax. `database.sql` defines the target database/table and matching fields. A caught PDO exception is logged and yields a 500 result; otherwise the handler displays success.
6. **The response returns to the browser.** The PHP helper emits an HTML result page with escaped dynamic heading/message, status code and a link back to `lelg.html#contact`; it links `styles.css`. Thus the flow is browser form → HTTP POST → PHP validation → config/PDO connection → SQL table insert → HTML response.

### File dependencies and boundaries

- `lelg.html` links `styles.css` and deferred `script.js`; it submits to `contact.php` and contains IDs those scripts query.
- `script.js` expects the menu, tip and contact-form elements to exist. Its comments refer to PHP as the next step, but the actual action is declared by the HTML form.
- `contact.php` requires `config.php`, expects a MySQL database/table compatible with its INSERT, links `styles.css` on its result page and links back to `lelg.html`.
- `config.php` returns host/database/username/password/charset values; it does not connect by itself.
- `database.sql` creates the database and `contact_messages` schema expected by the PHP INSERT. `IF NOT EXISTS` does not modify an existing schema.
- `styles.css` defines states such as `.is-open` and `[aria-invalid="true"]`, but does not itself toggle classes or set ARIA attributes; JavaScript/server markup would need to do that.

## Likely teacher questions and precise answers

**Q: Why have client-side and server-side validation?**

A: Client-side validation can give immediate feedback in the browser, but a visitor can bypass or alter it. PHP independently validates the received values before database insertion, so server-side checks determine what is accepted.

**Q: What does `novalidate` do here?**

A: It disables the browser’s automatic constraint-validation UI for the form. The JavaScript supplies custom client-side feedback, and PHP still validates on the server. It does not remove the input attributes themselves.

**Q: Why is `method="post"` used?**

A: It sends form data in the HTTP request body rather than appending it to a GET URL. The endpoint also explicitly accepts POST and responds with 405 for another method.

**Q: How does the mobile menu open?**

A: On click, JavaScript reads the current `aria-expanded` string, inverts the state, and calls `setMenuOpen`. That function updates `aria-expanded`, labels, and the `is-open` class. At widths up to 680px, CSS hides `.nav-links` unless it also has `is-open`.

**Q: Why use `defer` for the script?**

A: It lets HTML parsing complete before the external script executes, so the page elements it queries can be present when setup runs.

**Q: What does `textContent` achieve for the learning tip?**

A: It inserts the tip as text rather than parsing the string as HTML. The code then sets `hidden` to false to show the output element.

**Q: Why use a prepared statement?**

A: The SQL command has named placeholders and the submitted values are passed separately to `execute`, keeping data separate from SQL syntax and reducing SQL-injection risk.

**Q: What is the purpose of `config.php`?**

A: It returns connection settings in an associative array, taking truthy environment-variable values when present and otherwise using the local fallbacks. It does not establish a connection itself.

**Q: What happens when the database already exists?**

A: `CREATE DATABASE IF NOT EXISTS` avoids creating it again, but does not update its existing charset/settings. Likewise, `CREATE TABLE IF NOT EXISTS` does not alter or verify an already existing table definition.

**Q: Why use `utf8mb4`?**

A: It is the configured character set for broad Unicode text support. The database, table and PDO DSN configuration consistently specify it; the code does not prove the running server has been configured successfully.

**Q: Does `NOT NULL` mean a valid name or email is guaranteed?**

A: No. It prevents SQL NULL values in those columns. It does not ensure a string is nonempty or that an email is correctly formatted; PHP performs separate checks.

**Q: What happens if database insertion fails?**

A: PDO is configured to throw exceptions. The `catch` block logs the exception details to the server log and returns a general 500 result page. It does not display the raw exception to the visitor.

**Q: Can we tell why the author chose these particular design values?**

A: Not reliably. We can describe their technical effects—such as the 680px responsive threshold or a color variable—but personal motivation is not encoded by those effects. We should not invent it.
